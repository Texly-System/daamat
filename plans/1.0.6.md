# Damat 1.0.6 update plan

This is the implementation record for the accepted Damat 1.0.6 release batch.
It includes the original five patch updates, the dedicated Damat PostgreSQL
schema formerly collected for 1.2, and native pgvector support formerly tracked
as 2.0. Repository-wide validation, packing, and publication remain explicit
gates; this plan does not authorize publication.

## Status

- Release: `1.0.6`
- Phase: release assembly and cumulative verification complete
- Implementation: all seven accepted updates complete; coordinated manifests
  and `bun.lock` are at 1.0.6
- Publication: not approved or published

## Implemented updates

### 1. Restore environment-aware `nodeEnv` in generated backends

**Problem**

The backend scaffold currently writes a fixed development environment:

```ts
nodeEnv: "development",
```

That makes a generated backend report development behavior even when it runs
with `NODE_ENV=production`.

**Planned change**

Restore the generated configuration to:

```ts
nodeEnv: process.env.NODE_ENV === "production" ? "production" : "development",
```

This keeps local and unspecified environments in development mode while making
production mode follow `NODE_ENV=production`.

**Scope**

- Update the source template in
  `packages/cli/app/src/commands/create/scaffold/templates/damatConfig.ts`.
- Add scaffold coverage for both production and non-production behavior.
- Document the correction in the `@damatjs/cli-app` 1.0.6 release record.
- State in the upgrade note that existing generated backends must update their
  own `damat.config.ts`; regenerating a backend is not required.

**Acceptance criteria**

- A newly generated backend uses production mode only when
  `NODE_ENV === "production"`.
- A newly generated backend uses development mode when `NODE_ENV` is absent or
  has another value.
- No generated backend configuration hardcodes `nodeEnv: "development"`.

### 2. Make Git initialization optional for backend and module creation

**Problem**

The creation commands are inconsistent:

- `damat create` initializes a Git repository by default and already accepts
  `--no-git`.
- `damat module init` does not currently initialize a Git repository and has no
  Git option.

Users should get the same predictable Git setup and the same opt-out flag for a
new backend or standalone module.

**Planned change**

- Keep Git initialization enabled by default for `damat create`.
- Add Git initialization by default to `damat module init`.
- Support `--no-git` on both commands to create files without initializing a
  repository or making an initial commit.
- Make `--no-git` visible in command usage, help text, examples, and current
  creation documentation.
- Reuse one Git initialization implementation where practical so missing Git,
  initialization failures, branch naming, and warning behavior stay aligned.

The default initial branch will remain `main`. A missing Git executable or a
failed initial commit will warn without deleting the completed scaffold.

**Expected commands**

```bash
damat create my-api --no-git
damat module init inventory --no-git
```

**Scope**

- `@damatjs/cli-app`: retain and document the backend flag, including its usage
  synopsis.
- `@damatjs/cli-module`: add the boolean Git option and module initialization
  behavior.
- `@damatjs/cli-support`: host shared Git setup behavior if the implementation
  is extracted from the app CLI.
- `@damatjs/damat-cli`: verify the composed command help exposes both options.
- Add the affected package release records for 1.0.6 when implementation
  begins.

**Acceptance criteria**

- `damat create <name>` initializes Git and creates an initial commit by
  default.
- `damat module init <name>` initializes Git and creates an initial commit by
  default.
- Passing `--no-git` to either command performs no Git availability probe,
  initialization, staging, or commit.
- Git setup failure is non-fatal and leaves the scaffold usable.
- Git setup and dependency/database setup remain independently selectable.
- Unit tests cover default setup, `--no-git`, missing Git, failed setup, and
  command help for both creation paths.

### 3. Preserve repeated installer `--target` options

**Problem**

Module and Kit installation accept `--target capability=path`, and the
installer option adapter can already consume either one target string or an
array. The core command parser nevertheless treats every option as scalar, so
each repeated `--target` overwrites the previous value and only the final
destination reaches the installer.

**Planned change**

- Add an explicit repeatable/multiple marker to the core CLI option contract.
- Accumulate repeated values only for options carrying that marker.
- Mark the module and Kit `target` options as repeatable.
- Preserve the current scalar result for one occurrence and last-value behavior
  for every non-repeatable option.
- Support both `--target value` and `--target=value`, including mixed use in one
  command.

**Scope**

- `@damatjs/cli`: extend `CommandOption` and `parseCommandArgs()`.
- `@damatjs/cli-module` and `@damatjs/cli-kit`: mark their installer target
  options repeatable.
- `@damatjs/cli-support`: verify the accumulated values become one capability
  target map.
- `@damatjs/damat-cli`: verify repeated targets through the composed command
  path and help surface.
- Document the fix in the affected 1.0.6 release records.

**Acceptance criteria**

- `--target routes=src/http --target jobs=src/workers` reaches the installer as
  both overrides.
- Inline, separate, and mixed value syntax produce the same ordered values.
- A single target remains compatible with the current scalar input shape.
- Repeating a non-repeatable option retains its existing last-value behavior.
- Module and Kit planning and installation apply every supplied target.

### 4. Ignore invalid heuristic provider candidates for bare-source modules

**Problem**

Bare-source module resolution selects the first existing application or
module-local workflow, job, event, or pipeline candidate. An empty stale
application directory therefore shadows a valid module-local provider, even
though provider loading later rejects the selected directory for having no
`index.ts` or `index.js`.

This is limited to manifestless bare-source compatibility. Explicit
manifest-declared provider paths remain authoritative.

**Planned change**

- During bare-source heuristic resolution, select the first candidate that is
  actually loadable as a provider: a direct file or a directory containing a
  conventional `index.ts` or `index.js` entry.
- Continue to later module-local candidates when an earlier heuristic directory
  exists but is empty or invalid.
- Keep strict failure behavior for explicitly declared manifest paths so a bad
  declaration is never silently replaced.
- Share the provider-entry validity rule between resolution and runtime loading
  where practical to prevent the two stages from drifting.

**Scope**

- `@damatjs/installer`: harden bare-source provider candidate selection.
- `@damatjs/framework`: retain clear provider-load errors and share entry
  validation if ownership permits.
- `@damatjs/module` and `@damatjs/damat-cli`: verify assembled bare-source
  startup through the normal registry path.
- Document the compatibility correction in the affected 1.0.6 release records.

**Acceptance criteria**

- An empty application provider directory cannot shadow a valid module-local
  provider.
- A valid application-owned provider still has precedence over module-local
  fallbacks.
- Direct provider files and directory `index.ts`/`index.js` entries remain
  supported.
- An invalid explicit manifest provider path still fails with an actionable
  error.
- Regression coverage exercises workflow, job, event, and pipeline candidates.

### 5. Document and lock the current `event.wait` activation boundary

**Problem**

Pipeline `event.wait` nodes scan durable event history beginning at the node
execution's creation time. A matching event published before that node becomes
active is intentionally not selected, even when its correlation ID matches.
Current documentation calls event waits durable but does not state this history
boundary or contrast it clearly with signals, which may arrive before their wait
node activates.

**Planned change**

- Document that the current `event.wait` contract begins at node activation and
  excludes earlier facts.
- Document the safe start-work/await-completion graph: activate a correlated
  wait branch alongside the work branch, then join them.
- Explain that correlation narrows eligible events but does not move the
  history boundary backward.
- Add regression coverage that locks the existing activation-scoped behavior
  and proves the pre-armed fork/join pattern completes.
- Make no runtime matching change in 1.0.6. Any configurable earlier history
  boundary belongs to an additive minor-version API.

**Scope**

- `@damatjs/pipelines`: current README, internals, focused storage tests, and
  1.0.6 clarification note.
- Damat pipeline guide: event-wait timing, correlation, and fork/join example.

**Acceptance criteria**

- Documentation explicitly distinguishes early buffered signals from
  activation-scoped durable events.
- A test proves an event published before wait activation is not consumed.
- A test proves a correlated wait activated alongside the work branch consumes
  the later completion event and allows an `all` join to finish.
- No existing `event.wait` runtime semantics change in 1.0.6.

### 6. Move Damat infrastructure into the `damat` PostgreSQL schema

Framework-owned `_damat_*` relations move out of `public` and into a dedicated
`damat` schema. Application, module, and link tables remain in their configured
application schemas.

The migration tracker moves first during migration preflight. New forward-only
system migrations then relocate durability, jobs, events, and pipelines tables
with `ALTER TABLE ... SET SCHEMA`, preserving rows, identities, indexes,
constraints, grants, and cross-system foreign keys. Existing applied migration
definitions are not rewritten. Fresh databases and later capability enablement
remain supported through the same ordered catalogs.

Runtime, readiness, inspection, control, retention, acceleration, and
operational SQL must fully qualify framework relations as
`"damat"."_damat_*"`; runtime correctness must not depend on `search_path`.
Legacy system migrations may use a transaction-local compatibility search path
while they are applied, because their committed SQL remains immutable.

**Acceptance criteria**

- Fresh all-capability setup leaves no `_damat_*` relations in `public`.
- A populated 1.0.5 database upgrades without losing migration history or
  durable state.
- Durability, jobs, events, and pipelines capability subsets migrate and can be
  enabled later.
- Re-running setup is idempotent; source/target conflicts fail actionably.
- Startup before migration remains read-only and reports the migration command.
- Separate runtime roles are documented with `USAGE ON SCHEMA damat` and table
  privileges.
- Runtime tests prove behavior with a `public`-only search path.

### 7. Add native pgvector across the ORM

`columns.vector(dimensions)` now generates native PostgreSQL
`VECTOR(dimensions)` and `columns.halfVector(dimensions)` generates
`HALFVEC(dimensions)`. Module schemas infer the `vector` extension, and initial
or incremental migrations emit `CREATE EXTENSION IF NOT EXISTS vector` before
the first dependent table or column.

The contract includes explicit vector dimensions, finite/exact-length write
validation, TypeScript/Zod generation, pgvector client registration and
serialization, HNSW/IVFFlat index metadata, four distance operators, and
`repository.findNearest()`. Ordinary `columns.real().array()` and
`columns.doublePrecision().array()` remain PostgreSQL arrays.

Existing unapplied migrations that contain `REAL[]` for a declared
`columns.vector(2048)` must be regenerated. Existing applied REAL[] data needs
an application-reviewed conversion; automatic lossy casts are never emitted.
For Asset Inspiration and equivalent modules, generated SQL must contain, in
order:

```sql
CREATE EXTENSION IF NOT EXISTS vector;
-- ...
"embedding" VECTOR(2048)
```

**Acceptance criteria**

- The public `columns.vector(2048)` builder generates `VECTOR(2048)`, never
  `REAL[]`, with extension creation first.
- The same ordering holds when incrementally adding the first vector column.
- A second unchanged generation is empty and removing vectors never drops the
  extension.
- Runtime CRUD, filters, transactions, relations, and nearest queries serialize
  only modeled vectors and deserialize them as `number[]`.
- Exact dimensions and finite values are rejected before SQL.
- Real `pgvector/pgvector:pg16` integration covers round trips and cosine
  nearest-neighbor ordering.
