# Native pgvector scope — folded into 1.0.6

This plan turns Damat's existing `columns.vector()` compatibility helper into a
native PostgreSQL pgvector contract across models, migrations, runtime queries,
indexes, generated schemas, validation, and documentation.

This file preserves the detailed pgvector contract originally drafted under
2.0. The user has accepted it into Damat 1.0.6. The authoritative combined
release record is [the 1.0.6 plan](./1.0.6.md); there is no separate 2.0 release.
The REAL[]-to-VECTOR storage correction remains documented so existing data is
reviewed safely.

## Status

- Release: `1.0.6`
- Phase: implementation, release assembly, and cumulative verification complete
- Compatibility: accepted `columns.vector()` native-storage correction with
  an explicit migration review for existing REAL[] data
- Publication: not approved

## Resolved public contract

### Vector columns

```ts
embedding: columns.vector(1536);
compactEmbedding: columns.halfVector(2048);
```

- `columns.vector(dimensions)` maps to PostgreSQL `VECTOR(dimensions)`.
- `columns.halfVector(dimensions)` maps to PostgreSQL
  `HALFVEC(dimensions)`.
- Both APIs have the TypeScript representation `number[]`.
- Dimensions must be a positive integer. PostgreSQL remains authoritative for
  server/version-specific maximum dimensions.
- Vector columns are PostgreSQL scalar extension types, so their model metadata
  always has `array: false`.
- The generic `.array()` modifier must not turn vector or half-vector columns
  into `VECTOR[]`/`HALFVEC[]`.

Ordinary PostgreSQL arrays remain separate and unchanged:

```ts
samples: columns.real().array();
preciseSamples: columns.doublePrecision().array();
```

### Column metadata

Add explicit column types and dimensions:

```ts
type ColumnType = ExistingColumnType | "vector" | "halfvec";

interface ColumnSchema {
  // existing fields
  dimensions?: number;
}
```

`length` remains reserved for character/numeric concepts. Snapshots, diffs,
generated types, and validators must read vector size only from `dimensions`.

### Validation

All generated and runtime write boundaries must:

- require an array of numbers;
- require exactly the declared dimensions;
- reject `NaN`, `Infinity`, and `-Infinity`;
- preserve nullable and optional behavior;
- return `number[]` for reads and writes;
- reject invalid vector values before issuing SQL.

Direct ORM usage receives the same finite/dimension validation as generated
service schemas. Ordinary `REAL[]` and `DOUBLE PRECISION[]` continue through the
existing PostgreSQL-array path.

### Required PostgreSQL extensions

`ModuleSchema` gains backward-compatible, snapshot-persisted extension
requirements:

```ts
interface ModuleSchema {
  // existing fields
  extensions?: string[];
}
```

Schema construction derives and deduplicates `"vector"` when any vector or
half-vector column is present. Missing and empty extension lists compare equal
for older snapshots.

The schema diff has an additive `create_extension` change. Initial and
incremental migrations emit the following before enums or tables that may use
the type:

```sql
CREATE EXTENSION IF NOT EXISTS vector;
```

Removing the last vector column never generates `DROP EXTENSION`; other modules
or application SQL may still depend on it. The extension requirement remains in
the current snapshot so a second migration generation is empty.

### Column diffs and upgrades

Column equality and diff logic compare:

- `vector` versus `halfvec` type;
- `dimensions`;
- array state;
- nullability and defaults.

Type or dimension changes are never silently emitted as a lossy cast. Migration
generation adds a clear manual-review warning naming the table, column, old
type/dimensions, and new type/dimensions. Other safe changes on that column,
such as nullability/default changes, may still be emitted. Reverse diffs restore
dimensions, while extension creation is intentionally not reversed.

The manual-review case still produces a no-op migration comment and advances
the schema snapshot. That makes the warning durable in migration history while
preventing the same reviewed transition from reappearing on every subsequent
generation.

The 1.0.6 upgrade guide must call out existing `columns.vector()` snapshots and
require an application-reviewed data migration from `REAL[]` to native vector
storage.

## Distance queries

Add a repository API whose result shape cannot collide with a domain column
named `distance`:

```ts
type VectorDistance = "l2" | "cosine" | "innerProduct" | "l1";

const matches = await repository.findNearest({
  column: "embedding",
  vector: queryEmbedding,
  distance: "cosine",
  limit: 20,
  where: { embedding_model_revision: revision },
});

// Array<{ row: ModelRow; distance: number }>
```

Operator mapping is explicit:

| Distance       | PostgreSQL operator |
| -------------- | ------------------- |
| `l2`           | `<->`               |
| `cosine`       | `<=>`               |
| `innerProduct` | `<#>`               |
| `l1`           | `<+>`               |

The method:

- asserts that `column` is a modeled `vector` or `halfvec` column;
- validates the query vector with the modeled dimensions and finite-number
  rules;
- applies existing typed `where` compilation;
- orders ascending by the computed distance and applies a positive-integer
  limit capped at `1000`, matching the service pagination safety bound;
- returns `{ row, distance }`, never an ambiguously named similarity value.

Strict compile-time restriction to only vector column names is deferred unless
the model/repository generics are improved separately; the 1.0.6 implementation
must still retain typed distance names and enforce the modeled column at
runtime.

## Vector indexes

Extend the public index types:

```ts
type IndexType = ExistingIndexType | "hnsw" | "ivfflat";

type IndexColumn =
  | {
      name: string;
      expression?: never;
      operatorClass?: VectorOperatorClass;
      order?: "ASC" | "DESC";
    }
  | {
      name?: never;
      expression: string;
      operatorClass?: VectorOperatorClass;
      order?: "ASC" | "DESC";
    };
```

`IndexSchema` retains `where` and `concurrently` and adds storage parameters:

```ts
with?: Record<string, string | number | boolean>;
```

Required operator classes are:

- `vector_l2_ops`, `vector_cosine_ops`, `vector_ip_ops`, `vector_l1_ops`;
- `halfvec_l2_ops`, `halfvec_cosine_ops`, `halfvec_ip_ops`,
  `halfvec_l1_ops`.

Model example:

```ts
columns
  .indexes("search_embedding_hnsw")
  .columns([{ name: "embedding", operatorClass: "halfvec_cosine_ops" }])
  .type("hnsw")
  .with({ m: 16, ef_construction: 64 });
```

Expected SQL:

```sql
CREATE INDEX "search_embedding_hnsw" ON "asset"
USING hnsw ("embedding" halfvec_cosine_ops)
WITH (m = 16, ef_construction = 64);
```

Expression indexes support the pgvector high-dimensional pattern:

```ts
columns
  .indexes("search_embedding_halfvec_hnsw")
  .columns([
    {
      expression: "(embedding::halfvec(2048))",
      operatorClass: "halfvec_cosine_ops",
    },
  ])
  .type("hnsw");
```

The SQL generator must correctly place `CONCURRENTLY`, quote named columns but
not arbitrary SQL expressions, render operator classes/storage parameters, and
preserve partial predicates. Changed or removed indexes carry enough prior
metadata to honor concurrent drop behavior. The existing non-transactional
migration executor remains the owner of concurrent-index execution.

`cleanupIndexSchema()` must preserve every supported field, including
`concurrently`; this fixes the existing metadata-loss bug.

## PostgreSQL adapter lifecycle

Add official `pgvector` through the curated dependency package and expose it as
`@damatjs/deps/pgvector`. Runtime ORM code imports the node-postgres adapter from
that curated subpath.

The pgvector lifecycle must account for pools created before module migrations:

1. Attach best-effort registration for new physical clients when a vector-aware
   ORM client/entity manager is created.
2. Before every vector-aware ORM execution, acquire or use the exact
   `PoolClient`, await `pgvector.registerTypes(client)`, then run the query on
   that same client.
3. Cache successful registration per physical client, but never cache a failed
   pre-extension attempt. This lets a later query retry after migrations create
   the extension.
4. Release clients acquired from a pool after the query. Preserve caller-owned
   transaction clients.
5. Apply the same path to standalone `PgModelClient`, entity-manager
   repositories, service-managed pools, and externally supplied pools.

This avoids racing node-postgres's non-awaited async `connect` event listeners
and handles the standalone module harness, which may create the pool before the
migration that installs pgvector.

Serialize modeled vector and half-vector parameters with `pgvector.toSql()` in
insert, bulk insert, update, upsert conflict updates, vector conditions, and
nearest queries. Do not serialize ordinary PostgreSQL arrays through pgvector.
Registered clients deserialize both `VECTOR` and `HALFVEC` results to
`number[]`.

Finite-number and exact-dimension checks live in one ORM-model runtime helper.
The PostgreSQL serializer and service validation share that contract; generated
Zod emits the equivalent `z.array(z.number().finite()).length(dimensions)` form.

## Asset Inspiration acceptance case

The initial production choice is:

```ts
embedding: columns.halfVector(2048);
```

with HNSW cosine indexing:

```ts
columns
  .indexes("asset_embedding_hnsw")
  .columns([{ name: "embedding", operatorClass: "halfvec_cosine_ops" }])
  .type("hnsw");
```

Migration output includes, in order:

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE "asset" (
  -- other columns
  "embedding" HALFVEC(2048) NOT NULL
);

CREATE INDEX "asset_embedding_hnsw" ON "asset"
USING hnsw ("embedding" halfvec_cosine_ops);
```

Applications that require full single-precision storage and reranking may keep
`VECTOR(2048)` and create a half-vector expression index.

## Implementation phases

1. **Schema contract** — ORM column/index/module types and snapshots.
2. **Model builders** — vector/half-vector builders, dimensions, index metadata,
   cleanup, and TypeScript mapping.
3. **Codegen and service validation** — generated TypeScript/Zod plus runtime
   finite/dimension checks. The touched legacy service methods file must be
   split by responsibility as part of this phase so every resulting code file
   satisfies the repository's 100-physical-line limit without changing CRUD
   behavior.
4. **Processor and migration generation** — extension changes, DDL, diffs,
   warnings, indexes, and reverse behavior.
5. **PostgreSQL runtime and queries** — curated dependency, per-client
   registration, parameter serialization, deserialization, and nearest API.
6. **Integration and upgrade evidence** — real pgvector CRUD/query/index tests,
   second-generation no-diff proof, documentation, release records, packed
   manifests, and clean-consumer validation.

## Acceptance tests

- Model schema records `type: "halfvec"`, `dimensions: 2048`, and
  `array: false`.
- Invalid dimensions fail while valid positive integer dimensions persist.
- Initial migration emits the vector extension before table creation.
- A second migration generation has no diff.
- Incrementally adding the first vector column emits the extension before the
  column/table change.
- Removing vector columns never emits `DROP EXTENSION`.
- `VECTOR(1536)` and `HALFVEC(2048)` DDL are exact.
- HNSW/IVFFlat, operator-class, expression, storage-parameter, partial, and
  concurrent index DDL are exact.
- `IndexBuilder.concurrently()` survives schema cleanup and snapshot/diff.
- Insert, update, upsert, filter, and read paths return `number[]` and serialize
  only modeled vector values.
- Exactly 2048 finite values are accepted for the Asset Inspiration column.
- 2047/2049 values and non-finite values are rejected before SQL.
- Cosine nearest-neighbor ordering and returned distances work against
  PostgreSQL.
- Pool, transaction-client, externally supplied pool, and same-pool
  post-migration registration paths are covered.
- Integration tests use the existing `pgvector/pgvector:pg16` harness.
- Ordinary `REAL[]`/`DOUBLE PRECISION[]` remain supported and distinct.
- Documentation and 1.0.6 release notes identify the `columns.vector()` semantic
  change and the required data/snapshot migration review.
