## Planned updates

### 1. Move Damat infrastructure tables into a dedicated PostgreSQL schema

**Problem**

Damat's migration tracker, durability, job, durable-event, and pipeline tables
currently live in PostgreSQL's `public` schema. The `_damat_*` tables crowd the
same namespace as application, module, and link tables, making the application's
own schema harder to inspect and manage.

**Planned change**

- Create a dedicated PostgreSQL schema named `damat` for framework-owned
  database infrastructure.
- Move every Damat-owned `_damat_*` table out of `public` and into `damat`.
- Keep the existing table names in 1.0.6; for example,
  `public._damat_job_runs` becomes `damat._damat_job_runs`. This update changes
  ownership location, not durable data semantics.
- Fully qualify system-table SQL as `"damat"."_damat_*"` instead of depending
  on the connection's `search_path`.
- Leave application, module, and link tables in their existing application
  schema.

After a complete setup or upgrade, `public` should contain only
application-owned relations unless the application intentionally creates
something else there.

**Upgrade strategy**

- Add forward-only 1.0.6 migrations; do not rewrite any applied system
  migration.
- Create `damat` idempotently before any qualified system-table access.
- Upgrade the migration tracker first so its existing history moves from
  `public._damat_migration_logs` to `damat._damat_migration_logs` without losing
  records.
- Move existing tables with transactional `ALTER TABLE ... SET SCHEMA` steps so
  rows, indexes, constraints, identities, grants, and foreign-key relationships
  are preserved rather than copied or recreated.
- Make each move safe for both fresh databases and databases upgraded from
  earlier releases, including installations that enable only some durable
  capabilities.
- Fail with an actionable error instead of overwriting an incompatible existing
  `damat` schema or conflicting target relation.
- Document the required `USAGE` and table privileges for deployments that use
  separate migration and runtime PostgreSQL roles.

Production rollout order is migration first, then 1.0.6 API and worker
processes. Framework startup remains schema-read-only and must not move tables.

**Scope**

- `@damatjs/orm-migration`: create/upgrade the dedicated schema and relocate,
  read, and write the migration tracker through its qualified name.
- `@damatjs/durability`: migrate shared infrastructure and qualify durability,
  worker, control, idempotency, retention, and acceleration queries.
- `@damatjs/jobs`, `@damatjs/events`, and `@damatjs/pipelines`: add ordered
  relocation migrations and qualify every runtime, inspection, control,
  retention, and integration query.
- `@damatjs/framework`: qualify direct acceleration audit and projection
  queries.
- `@damatjs/orm-cli` and `@damatjs/module`: verify application migrations,
  standalone module setup, and the module harness work with the new schema.
- Update current database/migration documentation, operational examples, the
  reference backend, and each affected package's 1.0.6 release record.

**Compatibility and migration impact**

- Existing durable data and migration history must be preserved.
- Deployments must run `bun run db:migrate` before starting 1.0.6 runtime
  processes.
- Application or operational SQL that directly queries an internal
  `public._damat_*` table must switch to the qualified `damat._damat_*` name;
  supported headless inspection and control clients should continue unchanged.
- PostgreSQL roles that previously relied only on `public` access may need
  explicit access to the `damat` schema.

**Acceptance criteria**

- A fresh backend with all durable services has its Damat-owned relations in
  `damat` and has no `_damat_*` relations in `public`.
- Upgrading a populated earlier-release database preserves migration history,
  durable payloads, attempts, leases, schedules, controls, logs, and pipeline
  state.
- Upgrades also work when only durability, jobs, events, or pipelines are
  enabled.
- All indexes, identities, constraints, and cross-system foreign keys remain
  valid after relocation.
- Re-running database setup or migration is idempotent.
- Runtime and readiness code uses qualified system relation names and does not
  depend on `search_path`.
- Starting 1.0.6 before the required migration fails with clear migration
  guidance rather than a generic missing-table error.
- Tests cover fresh setup, a data-bearing earlier-release upgrade, capability
  subsets, schema-name conflicts, separate-role permissions, and direct runtime
  work after migration.
