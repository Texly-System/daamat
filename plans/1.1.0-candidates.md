# Damat 1.1.0 candidate backlog

This file is the collection point for work that may enter the next minor
release. An item appearing here is not a commitment to ship it in 1.1.0.
Accepted work moves to the affected package's `releases/<package>/next.md`
only when implementation begins.

## Current candidates

### Model-aware CRUD generation policies

- Add an explicit per-model generation policy such as `crud`, `readOnly`,
  `appendOnly`, or `commandOnly`.
- Generate only the accessors, steps, workflows, routes, schemas, and exports
  permitted by that policy.
- Define how regeneration removes obsolete generated mutations without
  deleting hand-authored domain commands.
- Prove mixed-policy modules and repeated generation are deterministic.

### Safe workflow-to-HTTP error bridge

- Provide a framework helper for translating known workflow failures into
  stable HTTP errors without exposing arbitrary nested causes or raw messages.
- Unwrap only framework-owned wrappers and explicitly approved application
  error classes or predicates.
- Define mappings for validation, not-found, conflict, timeout, and unknown
  failures.
- Test the full route to workflow to step path, including hostile cause chains.

### First-class bounded request-body API

- Add an explicit API for bounded JSON and raw request-body consumption.
- Enforce encoded-byte limits before full materialization, including chunked
  requests.
- Define stable behavior for invalid UTF-8, malformed JSON, aborted streams,
  exact-limit bodies, and oversized bodies.
- Preserve the 1.0.4 rule that routes do not parse undeclared bodies eagerly.

### Explicit pipeline event-history boundaries

- Problem and evidence: `event.wait` currently scans from the wait node
  execution's creation time, so a correlated completion fact published after a
  run or branch starts but before the wait node activates cannot match.
- Affected packages and public APIs: `@damatjs/pipelines` node definitions,
  runtime matching, authoring validation, documentation, and inspection detail.
- Proposed additive behavior: let a graph establish an explicit safe history
  boundary, or provide an atomic pre-arm-and-dispatch primitive for the common
  start-work/await-completion pattern.
- Compatibility and migration risk: keep activation time as the default
  throughout 1.x; do not broaden existing waits silently because that could
  consume stale facts. Require strong correlation when selecting earlier
  history.
- Required tests: publish a uniquely correlated fact between work dispatch and
  wait-node creation, restart the router, and prove exactly one match; also
  cover stale facts, duplicate facts, retention, and concurrent runs.
- Consumer reproducer: the audio processor's queued alignment work can publish
  its completion before a sequential event-wait node is created.
- Open decisions: explicit timestamp/reference expression, run/branch anchor,
  persisted subscription record, or a higher-level atomic graph primitive.

### Portable installed-test evidence and host adapters

- Problem and evidence: source installation copies standalone module tests into
  the backend test tree, but those tests may retain module-root relative paths,
  package aliases/configuration, database assumptions, and a one-module-per-
  process harness contract. Generated backends discover the copied files as
  ordinary TypeScript and Bun tests.
- Affected packages and public APIs: the `damat.json` test capability,
  `@damatjs/installer`, `@damatjs/cli-module`, generated module tests, generated
  backend receiver/test configuration, validation, and provenance records.
- Proposed additive behavior: distinguish immutable upstream test evidence from
  explicitly host-runnable compatibility tests, with an opt-in, declared
  adapter contract when conversion is safe.
- Compatibility and migration risk: never silently rewrite source tests; define
  how legacy `tests` capabilities are classified and keep existing lockfile
  ownership/provenance intact.
- Required tests: install one and several freshly generated modules into a
  freshly generated backend, then run backend type checking and test discovery;
  verify evidence is preserved without accidental execution and declared host
  tests run without harness collisions.
- Consumer reproducer: the audio backend preserves module suites under
  `tests/upstream/<id>` and excludes them while maintaining backend-owned
  compatibility and integration tests separately.
- Open decisions: new capability name versus test metadata, receiver defaults,
  adapter ownership, and whether publication validation must require portable
  host tests or only standalone evidence.

## Investigation before acceptance

### Complete the exact numeric runtime contract

- Audit `numeric`, `decimal`, `bigint`, `bigserial`, arrays, and generated
  validators across static types and real PostgreSQL round trips.
- Evaluate whether a module-level representation policy would improve the
  current per-column `.representation("string")` option.
- Keep the existing default representation throughout 1.x unless an additive,
  source-compatible design is demonstrated.
- Add a consumer reproducer before promoting any change into release work.

## Not candidates for 1.1.0

- Changing the default numeric representation from `number` to `string` would
  change generated and runtime types; treat that as a major-version decision.
- Changing timestamp or soft-delete defaults would alter persisted semantics;
  treat that as a major-version decision.

## Promotion gate

Before accepting a candidate for the release:

- Confirm a real consumer use case or reproducible gap.
- Classify the semver impact and exclude breaking defaults from the minor.
- Agree on the public API and ownership boundary.
- Identify affected package docs, guide pages, and release notes.
- Define unit, integration, PostgreSQL, and clean-consumer coverage as needed.
- Record the decision here, then move accepted work to the affected package's
  release plan when implementation begins.
