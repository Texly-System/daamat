# @damatjs/orm 1.0.6

> The ORM umbrella re-exports native pgvector modeling, migrations, indexes, and typed nearest-neighbor queries.

## What changed

The coordinated ORM packages now treat pgvector as a native PostgreSQL
extension type. `columns.vector(dimensions)` produces `VECTOR(dimensions)` and
`columns.halfVector(dimensions)` produces `HALFVEC(dimensions)` while both use
`number[]` in TypeScript. The model snapshot stores an explicit vector type and
dimension instead of overloading ordinary array metadata. Migrations add the
`vector` extension before dependent tables, preserve the requirement in
snapshots, and generate HNSW/IVFFlat index metadata (operator classes,
expressions, storage parameters, predicates, and concurrent creation).

The PostgreSQL adapter registers pgvector on each pool client, serializes
modeled vectors, decodes results to `number[]`, and provides typed nearest-
neighbor queries for L2, cosine, negative inner product, and L1 distance. Code
generation and service/runtime validation require finite arrays with exactly the
declared dimensions.

## Added

- Native `vector` and `halfvec` model metadata and exact dimension validation.
- Additive extension DDL and snapshot tracking for `vector`.
- HNSW/IVFFlat indexes and typed `findNearest` distance queries.
- Aggregate documentation for the Asset Inspiration choice of `HALFVEC(2048)`
  with HNSW cosine indexing, plus a full `VECTOR(2048)` halfvec expression
  index option for reranking.

## Changed / improved

- Ordinary `columns.real().array()` and `columns.doublePrecision().array()`
  remain ordinary PostgreSQL arrays and are no longer conflated with vectors.
- Vector dimension/type transitions are surfaced for manual review rather than
  silently cast or truncated.

## Compatibility note

- `columns.vector(dimensions)` is a semantic break. Before 1.0.6 it described a
  `REAL[]` column with the dimension stored in `length`; in 1.0.6 it describes a
  native `VECTOR(dimensions)` column with `type: "vector"`, `array: false`, and
  `dimensions`. Applications that intend to keep `REAL[]` must use
  `columns.real().array()` explicitly.

## Action required

1. Review every existing `columns.vector(n)` declaration. Keep it for native
   pgvector storage, or change it to `columns.real().array()` for a regular
   `REAL[]` column.
2. Install/enable the PostgreSQL `vector` extension and apply the generated
   migration. Extension creation is additive; generated migrations never drop
   it.
3. Review generated comments for vector type/dimension transitions and write an
   explicit data-safe SQL migration when changing them.
4. Review ANN indexes and choose `HALFVEC(2048)` + HNSW cosine or the full
   `VECTOR(2048)` + halfvec expression option appropriate for the workload.
